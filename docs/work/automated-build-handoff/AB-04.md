## Do these steps in order

1. Implement a small runtime tool registry: static analysis, secrets, and dependency audit for the first supported Node web-app profile. Inspect bundled scripts before reuse. Never edit signed content files by hand.
2. Run tools through the existing sandbox with fixed executable/argument templates, deadlines and bounded output. Tool commands are selected by trusted adapter code, not generated by a model. Do not substitute verify=true.
3. Use structured results and adapter-specific exit-code interpretation. Tool found vulnerabilities is different from tool failed to run. Missing executable, missing rules/database, timeout, invalid JSON and unavailable network produce ERROR/UNAVAILABLE, not PASS.
4. Run dependency audit only under the selected network policy. Local-only needs an available local advisory snapshot to claim a completed audit; otherwise disclose unavailable coverage. Never silently call a cloud advisory service.
5. Expose the same tool registry to both onboard analysis and the build verification path. Model specialists receive actual tool results for interpretation; a specialist named semgrep-runner is not itself evidence Semgrep ran.
6. CI injects process results/fixtures; a separate opt-in smoke run may exercise installed tools. No auto-installation or downloaded rule changes in unit tests.

## Acceptance — all must hold

- [ ] Fixtures distinguish clean scan, findings, timeout, unavailable tool and malformed output.
- [ ] A planted defect is detected by an actual selected tool in the opt-in smoke path; mocked adapter tests alone are not reported as that proof.
- [ ] Local-only policy prevents network access; absent advisory data is visible and blocks a required dependency check.
- [ ] Both onboard and build paths invoke the registry; plain model completion cannot manufacture scanner evidence.
