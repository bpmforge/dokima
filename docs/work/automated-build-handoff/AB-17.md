## Do these steps in order

1. First write the benchmark protocol with the exact tasks and scoring before collecting results. Use 5 small web-app tasks, each with a change request, three repeats per configuration.
2. Compare same model/runtime on the same inputs with and without Dokima guardrails. Keep hardware, model settings and task tests fixed. Include a known-defect ground truth and hidden acceptance tests.
3. Record completed acceptance criteria, false blocks, defect recall/false positives, wall time, calls/tokens/cost, retries, human interventions and whether main was changed. Infrastructure failures remain in denominators with their own label.
4. Do not launch paid models or recruit/message users from this coding handoff. Produce runnable evaluation instructions; run live only within explicitly supplied endpoints/budgets. Network-free CI stays separate.
5. For private beta require all mechanical red tests passing, reproducible supported configuration, zero false automatic acceptances in the bounded test set, and at least one observed novice finishing the journey. Describe these as limited pilot evidence, not security certification.
6. If thresholds fail, file specific reproduction tickets instead of expanding product scope or tweaking scoring after the fact.
