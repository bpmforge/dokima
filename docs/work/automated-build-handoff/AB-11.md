## Do these steps in order

1. Use the existing rejectTicket verb under the reviewer identity to return in_review work to ready. Never write ticket status directly and never impersonate the maker to reject.
2. Pass the normalized repair batch into the next maker handoff via existing rejection feedback. Retain the ticket worktree and verified base; do not reset/delete user work.
3. Limit automatic review-repair rounds to 3 total by default, additionally constrained by existing session/token/time budgets. An existing tighter bound wins. Track the count durably per ticket/source lineage so restart does not reset it.
4. After each repair rerun affected checks and their dependencies, close through the existing gate, and review the new head. One maker writer per ticket; reviewer checks can be grouped.
5. If findings and source are unchanged for two attempts, stop early. Provider outage is not a code defect: use bounded infrastructure handling without multiplying nested retries.
6. On exhaustion or scope/policy conflict, retain artifacts and emit one actionable decision with attempted fixes and remaining defects. Other independent tickets may continue.

## Acceptance — all must hold

- [ ] Planted failing check -> review rejection -> maker fix -> independent rerun -> fresh confirmed result occurs without a person intervening.
- [ ] Persistent defect ends at the bound; restart cannot grant 3 new rounds.
- [ ] Maker cannot reject as verifier; out-of-scope changes never auto-expand the ticket.
