## Do these steps in order

1. Reuse existing phase/decision receipts to establish approved design and stories. Inspect their real types first. An artifact existing on disk is not proof that the user approved it.
2. Build a canonical input digest for design, stories, acceptance, ticket dependency/write scopes, model policy and budget. Store a versioned approval event with the human actor and those digests. Do not include credentials.
3. Use a new explicit opt-in at the existing build-start API; old autonomy=auto alone is insufficient. Do not create a new unrelated settings store.
4. Validate the approval in a shared function invoked from executeBuildRun so CLI and HTTP cannot disagree. Refuse an invalid snapshot before claiming any ticket. Approval is tied to this project/run intent.
5. On a resumed run permit completed statuses and new evidence to change; hash the approved specification, not mutable execution status. Any material specification change needs renewed approval. Carry the validated policy into the runtime, not the raw HTTP body.

## Acceptance — all must hold

- [ ] API and CLI refuse missing/stale approval before claims on the opted-in path.
- [ ] Changing story text, acceptance, write scope, model policy or budget invalidates the approval; ticket progress does not.
- [ ] Legacy runs preserve existing behavior; a legacy auto flag cannot turn on the new pipeline.
