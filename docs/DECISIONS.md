| D-022 | 2026-08-03 | **License: FSL-1.1-ALv2** (Functional Source License, Apache-2.0 future licence) for Dokima's own source, superseding D-017. | D-023 | 2026-08-04 | **Dokima runs its own agent sessions, through the gateway.** A ticket session is a TOOL-USING LOOP this product owns: the gateway sends the handoff plus a tool schema to the role's model, executes the returned tool calls against the ticket worktree, and iterates until the model emits a Completion Manifest. An external agent CLI (`--agent-command`, `createChildProcessSpawn`) is demoted to an explicit ESCAPE HATCH for people who already have an agent they trust — never the default, and never the only path. | Shell out to an external agent CLI (opencode / claude / aider) as the primary session runner; ship no agent at all and require one; MCP-only tool execution | **Founder decision 2026-08-04** (Brad: "why are we wiring it to opencode? shouldn't we have our own api"). The recommendation on the table was opencode + a local model, chosen for expedience, and it was wrong on the architecture's own terms: ARCHITECTURE.md §4 says model calls go **via gateway, which "routes + meters every call"**, and the gateway owns the role→model matrix (FR-G2/W2-05), the R0–R4 escalation ladder (D-018), the budget breakers (W2-07) and spend metering. Delegating inference to a foreign CLI bypasses **all four**: the matrix stops deciding anything, the ladder never fires, the breakers cannot break, and the spend ledger goes blind because Dokima never sees the tokens. W7's memory/playbook injection goes with it. That reduces Dokima to a wrapper around someone else's agent while still claiming to be the harness that proves the work. The gates (SC-01/SC-02, maker≠verifier, receipts) are worth defending precisely because Dokima owns the whole loop. **CORRECTED 2026-08-04 by a challenge pass, before any code:** the first draft of this row justified putting the session in `apps/server` because "`packages/loop` may not import `gateway`, so no package can host it". That is false — `packages/harbormaster` already DECLARES both `@dokima/gateway` and `@dokima/loop`, and it already owns the claim loop that consumes a `SpawnSession`. The session belongs there. The draft also specified a bespoke tool allowlist, duplicating `packages/mcp` (W6-04), which already ships per-role allowlists, an approval policy and audited tool-call events. Reuse it. **Cost of the decision, stated honestly:** `ChatRequest` has no `tools` field today — tool calling was anticipated (`FinishReason` already includes `'tool_calls'`) and never built — so this is a milestone, not a wire. **It also resolves W10-77's piece 3**, which correctly said a gateway *completion* cannot be an agent because it changes no files; a gateway *tool loop* does. |
| D-024 | 2026-08-13 | **Model policy is USER-SELECTED CONFIGURATION, not a product law. AMENDS C-1 and D-018.** A user picks how their work is modelled: (a) **local-only** — never contacts a cloud provider, and the whole product still works; (b) **a specific model of their choosing**, local or cloud, pinned, no escalation; (c) **cheapest-first with escalation** across the providers they configured (D-018 `ladder`); or (d) escalation gated on approval (D-018 `token-gated`). **Local-only remains a GUARANTEED-SUPPORTED configuration — a feature that silently requires a cloud model is a bug (FR-G5 honest WAIVED degradation still binds) — but it is no longer the MANDATED default, and "cloud providers are integrations, never prerequisites" is restated as a capability guarantee rather than a prohibition.** **There is no silent default:** a fresh install asks in the setup wizard and nothing spends money, or contacts a network, until the user has chosen. | Local-first as a hard constraint with the ladder as an unchosen default; cloud-first with local as a fallback; a single global policy rather than per-role/scope | **Founder decision 2026-08-13** (Brad: "our rule of using local first and then escalating up, that's not really a rule so we need to fix that contract... they can use an LLM of whatever they are choosing... It is an optional based system"). C-1 encoded three different things under one word and enforced all of them as a hard, gate-blocking constraint: a CAPABILITY guarantee (it can run offline), a DEFAULT POLICY (what it does when nobody chose), and a DEV/CI DISCIPLINE (tests use fixtures and a fake model, never live API calls). Only the first survives as a guarantee; the second becomes an explicit user choice; **the third is untouched and stays hard — it is a testing rule, not a user-facing policy, and CLAUDE.md law 9 is split accordingly so the two can never be conflated again.** **Cost of the decision, stated honestly:** option (b) does not exist today in any usable form. D-018's `locked` mode pins a RUNG, not a model, and `providerForConfig` refuses `anthropic`/`openai`/`vertex`/`copilot` outright as "registered but not yet constructible" — they need a keychain-resolved credential and a real price table. So the single option a paying user is most likely to want is the one that is unimplemented, which makes W12-11/W12-12 release blockers rather than enhancements. The three-scope (run > project > global) per-role resolution D-018 already built is the right mechanism and is kept unchanged. |
| D-025 | 2026-08-13 | **A ticket names its expert in an explicit `role` field, set at DECOMPOSITION.** The planner that decides what a ticket IS also decides which of the 93 experts does it; the field is optional on the board (absent => `coding-agent`, today's behaviour) but validated against `content/` when present, and an unknown role fails the board validator by name rather than silently falling back. | Infer the role from `lane`/`module`; have a model read the roster and choose | **Founder decision 2026-08-13**, chosen over two alternatives that were put up with their costs. Lane/module inference needs no schema change and works today, but collapses 93 experts onto ~11 lanes — `security-auditor` and `db-architect` could never both serve `core` — so it structurally caps the expert library at the granularity of the parallelism contract, which is a different thing entirely. Model-side selection is the most capable and handles tickets no static map anticipated, but it is a model decision INSIDE the trust boundary (C-2/C-3): under Law 4 it would need its own receipt, and it spends a call per ticket before any work starts. The explicit field is deterministic, auditable, and cheap. **Fixes the defect that 93 experts shipped and exactly one was ever dispatched**: `defaultHandoffBuilder(role = ROLE_CODING_AGENT)` is called with no argument at every production call site. **Scope note:** W12-06 makes the field exist, be validated and be honoured; teaching the decomposer to EMIT it is a follow-up, and until then a human sets it by hand. C-4 is untouched — naming a maker role never lets the maker verify. |
